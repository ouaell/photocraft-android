# Decision 011 — GPU device limits (SU-9/F26 fix), the fallback notice on the rung matrix, knobs release-safety, SDK 36 + API matrix

- **Question (user correction 2026-10-21, M1 gate held open):** why did every emulator rung in `emulator-e2e-39523080709` show the "Switched to CPU rendering" dialog; is that expected, and does the shell create its wgpu device the way `apps/photocraft/src/gpu_startup.rs::configure` does (PORT-SPEC SU-8/SU-9)? Additionally: knobs must be debug-only, SDK levels per user decision, and CI must cover API levels 31/34/36.

- **Verified root cause (pinned sources, R14/R5 — not hypothesis):**
  1. **The notice on all three rungs is pinned upstream's own startup semantics for software-only adapters.** `apps/photocraft/src/main.rs:415-418`: `let software_window = rs.adapter.get_info().device_type == DeviceType::Cpu;` … `if software_window && mode != RenderingMode::Cpu { info.fallback = Some("No compatible hardware graphics adapter; using software graphics.") }` — then `main.rs:430-437` queues the notice when `gpu_info.canvas == "cpu"` and `mode != Cpu`. The emulator's only adapters are SwiftShader (`device_type Cpu`, backend Vulkan) and SwiftShader-over-`GL`, so the desktop app would run the CPU compositor and show the same dialog at the same place; our shell mirrored this block (and its message string) faithfully. The alternative premise — "raised only for a set_wgpu panic, a GPU fault, or the startup planner" — does not match the pinned source; this contradiction is recorded here per R14.
  2. **SU-9 was violated and is now fixed.** The shell passed `NativeOptions { ..Default::default() }`, so the device was requested with egui's default descriptor: egui-wgpu 0.36.2 `setup.rs:260-277` sets `max_texture_dimension_2d: 8192` over `Limits::default()` (GL base = `downlevel_webgl2_defaults()`), instead of the adapter's own texture/buffer limits. The desktop app installs `photocraft_ui_egui::gpu_canvas::use_adapter_limits_with(setup, on_adapter)` (`apps/photocraft/src/gpu_startup.rs:323`), backed by `gpu_canvas::device_limits(adapter)` (`crates/ui-egui/src/gpu_canvas.rs:811-815`). `WgpuConfiguration::default().wgpu_setup` is `WgpuSetup::without_display_handle()` (egui-wgpu `lib.rs:383-416`), so mutating it in place hits the `CreateNew` arm exactly like on desktop.
  3. **Behavior change expected from the SU-9 fix on the emulator: none.** Both limit sets are within the adapter's own limits on SwiftShader; device creation succeeded before and after (also visible in the old runs: render state existed, our adapter line logged). The fix matters for future hardware/documents (adapter's 16384 px texture limit instead of egui's 8192; the desktop comment at `main.rs:346` documents why: large documents stay on the GPU compositor).

- **Decision:**
  1. The shell now calls `photocraft_ui_egui::gpu_canvas::use_adapter_limits(&mut options.wgpu_options.wgpu_setup)` before `run_native` (SU-9 parity; desktop-only configure pieces — Intel DX12 default, Mac indirect-validation skip, marker-on-adapter hook, sentinel state — have no M1 counterpart; the SU-8 marker state machine remains a later milestone).
  2. The startup refusal on a software-only adapter stays exactly as pinned (desktop-identical): the directive's OR branch is taken — the named environmental reason is *SwiftShader-only adapters (device_type Cpu)* on the api-34 google_apis image, evidence = the per-rung `device request:` / `SystemInfo:` logcat lines plus pinned `main.rs:415-437` citations. `set_wgpu` isn't called there by upstream design, so "Image compositor: GPU" cannot be produced on this image; the open duty for a GPU result is a device/matrix with real adapters (M7), not a change to pinned app semantics.
  3. Help › System Info is captured per rung from logcat: the shell logs the same strings `gpu_status::system_info(&app)` produces (`crates/ui-egui/src/gpu_status.rs:62-88`), because tappable "Help" needs a wider window than the 320 px default AVD surface; menu automation is a later-milestone nicety, not M1 evidence. `scripts/e2e-rung.sh` turns missing `Picsh: SystemInfo: Image compositor: ` or missing `Picsh: device request: ` lines into a red rung.
  4. `getconf PAGE_SIZE` is captured per rung (`pagesize.txt`); the static 16 KB evidence (ELF `-Wl,-z,max-page-size=16384`, `zipalign -c -P 16 4`) is the M1 claim; *dynamic* 16 KB-page emulator testing is not claimed at M1 unless a 16 KB system image rung is added later.
  5. Knob assets move to the debug-only Gradle source sets `app/src/rungGlesDebug/assets` + `app/src/rungCpuDebug/assets` (`<flavor><BuildType>` camel naming); release variants of every flavor cannot bundle them. build.yml asserts: `picsh-knobs.txt` present in `rungGles/debug`, absent in `rungGles/release` and `rungDefault/release`.
  6. User decisions applied 2026-10-21: minSdk 31 / targetSdk 36 (compileSdk 36; AGP 9.0.1 supports API ≤ 36.1 per its release notes, so the 9.0.1/9.1.0 pair stands) and CI API levels 31/34/36 (full 3-rung matrix at 34; rungDefault boots at 31 and 36).

- **What would invalidate:** an upstream pin bump that changes `main.rs:415-437`'s gate or `device_limits`; an emulator image with non-Cpu adapters (then the default rung expectation becomes "Image compositor: GPU"); a Gradle/AGP change to variant source-set naming.

- **Sources:** `apps/photocraft/src/main.rs:415-437` at pin d43db3e1; `apps/photocraft/src/gpu_startup.rs:281-336`; `crates/ui-egui/src/gpu_canvas.rs:786-815, 869-962` (GpuInfo/`lines()` = Help › System Info); `crates/ui-egui/src/gpu_status.rs:62-93`; egui-wgpu 0.36.2 `setup.rs:240-280`, `lib.rs:383-416` (docs.rs source of the locked version); developer.android.com AGP 9.0.1 release notes (max API 36.1).
