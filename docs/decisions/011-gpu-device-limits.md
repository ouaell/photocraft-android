# Decision 011 — GPU device limits (SU-9/F26 fix), the fallback notice on the rung matrix, knobs release-safety, SDK 36 + API matrix

- **Question (user correction 2026-10-21, M1 gate held open):** why did every emulator rung in `emulator-e2e-39523080709` show the "Switched to CPU rendering" dialog; is that expected, and does the shell create its wgpu device the way `apps/photocraft/src/gpu_startup.rs::configure` does (PORT-SPEC SU-8/SU-9)? Additionally: knobs must be debug-only, SDK levels per user decision, and CI must cover API levels 31/34/36.

- **Verified root cause (pinned sources, R14/R5 — not hypothesis):**
  1. **The notice on all three rungs is pinned upstream's own startup semantics for software-only adapters.** `apps/photocraft/src/main.rs:415-418`: `let software_window = rs.adapter.get_info().device_type == DeviceType::Cpu;` … `if software_window && mode != RenderingMode::Cpu { info.fallback = Some("No compatible hardware graphics adapter; using software graphics.") }` — then `main.rs:430-437` queues the notice when `gpu_info.canvas == "cpu"` and `mode != Cpu`. The emulator's only adapters are SwiftShader (`device_type Cpu`, backend Vulkan) and SwiftShader-over-`GL`, so the desktop app would run the CPU compositor and show the same dialog at the same place; our shell mirrored this block (and its message string) faithfully. The alternative premise — "raised only for a set_wgpu panic, a GPU fault, or the startup planner" — does not match the pinned source; this contradiction is recorded here per R14.
  2. **SU-9 was violated and is now fixed.** The shell passed `NativeOptions { ..Default::default() }`, so the device was requested with egui's default descriptor: egui-wgpu 0.36.2 `setup.rs:260-277` sets `max_texture_dimension_2d: 8192` over `Limits::default()` (GL base = `downlevel_webgl2_defaults()`), instead of the adapter's own texture/buffer limits. The desktop app installs `photocraft_ui_egui::gpu_canvas::use_adapter_limits_with(setup, on_adapter)` (`apps/photocraft/src/gpu_startup.rs:323`), backed by `gpu_canvas::device_limits(adapter)` (`crates/ui-egui/src/gpu_canvas.rs:811-815`). `WgpuConfiguration::default().wgpu_setup` is `WgpuSetup::without_display_handle()` (egui-wgpu `lib.rs:383-416`), so mutating it in place hits the `CreateNew` arm exactly like on desktop.
  3. **Behavior change expected from the SU-9 fix on the emulator: none.** Both limit sets are within the adapter's own limits on SwiftShader; device creation succeeded before and after (also visible in the old runs: render state existed, our adapter line logged). The fix matters for future hardware/documents (adapter's 16384 px texture limit instead of egui's 8192; the desktop comment at `main.rs:346` documents why: large documents stay on the GPU compositor).

- **Decision:**
  1. The shell now calls `photocraft_ui_egui::gpu_canvas::use_adapter_limits(&mut options.wgpu_options.wgpu_setup)` before `run_native` (SU-9 parity; desktop-only configure pieces — Intel DX12 default, Mac indirect-validation skip, marker-on-adapter hook, sentinel state — have no M1 counterpart; the SU-8 marker state machine remains a later milestone).
  2. The startup refusal on a software-only adapter stays exactly as pinned (desktop-identical): the directive's OR branch is taken — the named environmental reason is *SwiftShader-only adapters (device_type Cpu)* on the api-34 google_apis image, evidence = the per-rung `device request:` / `SystemInfo:` logcat lines plus pinned `main.rs:415-437` citations. `set_wgpu` isn't called there by upstream design, so "Image compositor: GPU" cannot be produced on this image; the open duty for a GPU result is a device/matrix with real adapters (M7), not a change to pinned app semantics.
  3. Help › System Info is captured per rung from logcat: the shell logs the same strings `gpu_status::system_info(&app)` produces (`crates/ui-egui/src/gpu_status.rs:62-88`), because tappable "Help" needs a wider window than the 320 px default AVD surface; menu automation is a later-milestone nicety, not M1 evidence. `scripts/e2e-rung.sh` turns missing `Picsh: SystemInfo: Image compositor: ` or missing `Picsh: device request: ` lines into a red rung.
  4. `getconf PAGE_SIZE` is captured per rung (`pagesize.txt`); the static 16 KB evidence (ELF `-Wl,-z,max-page-size=16384`, `zipalign -c -P 16 4`) is the M1 claim; *dynamic* 16 KB-page emulator testing is not claimed at M1 unless a 16 KB system image rung is added later.
  5. Knob assets move to the debug-only Gradle source sets `app/src/rungGlesDebug/assets` + `app/src/rungCpuDebug/assets` (`<flavor><BuildType>` camel naming); release variants of every flavor cannot bundle them. build.yml asserts: `picsh-knobs.txt` present in `rungGles/debug`, absent in `rungGles/release` and `rungDefault/release`.
  6. User decisions applied 2026-10-21: minSdk 31 / targetSdk 36 (compileSdk 36; AGP 9.0.1 supports API ≤ 36.1 per its release notes, so the 9.0.1/9.1.0 pair stands) and CI API levels 31/34/36 (full 3-rung matrix at 34; rungDefault boots at 31 and 36).

- **Amendment 1 (2026-10-21, first e2e red of this step, run 39544194618 — NOT hypothesis):** `rungDefault` at **api 31** died before any window with `Picsh: eframe run failed: WGPU error: Limit 'max_storage_buffer_binding_size' value 134217728 is better than allowed 0` (`rungs/default-api31/logcat-full.txt` in artifact `emulator-e2e-39544194618`; pid 2661 stayed alive with no content). Root cause: `device_limits` keeps egui's base limits for every field except texture and buffer (pinned `gpu_canvas.rs:811-815`), and egui's non-GL base (`Limits::default()`, egui-wgpu `setup.rs:260-277`) requests `max_storage_buffer_binding_size = 128 MiB`; the api-31 image's older SwiftShader Vulkan adapter reports an allowed maximum of **0** for that limit, so device creation fails — the desktop app would fail identically on that adapter (upstream has no rescue for a device-request failure either). Fix (shell-only, no vendored logic): the shell installs its own `WgpuSetup::CreateNew.device_descriptor` (pub field, egui-wgpu 0.36.2 `setup.rs:206-207`; the closure shape mirrors pinned `gpu_canvas.rs:803-806`) which takes `gpu_canvas::device_limits(adapter)` and clamps **every** field down to the chosen adapter with wgpu 30.0.1's own public clamp `Limits::or_worse_values_from(&adapter.limits())` (docs.rs wgpu 30.0.1: "This function is for clamping requests for values beyond the supported limits"). Semantics: whenever the adapter is at least as good as egui's base, the request is byte-identical to desktop's; only incapable fields (storage 0 here) get lowered to what the hardware can do — the egui canvas needs none of them by default. Evidence lines in `Picsh: device request:` now also record requested/adapter `max_storage_buffer_binding_size`. Valve remained valid: api-34's three rungs were green in the same run, proving adapter/device-request/SystemInfo logging and the OR-branch verdict.

- **Amendment 3 (2026-10-21, user option 5, approved after the R4 report):** the amendment-1 **clamp is REVERTED** (directive 1) - a clamped device whose `max_storage_buffer_binding_size` is 0/…below the egui base cannot carry egui's buffer requests, so the clamped device only moved the failure from device creation to the first window target (evidence: run 39551410480, api-31 `panicked at` inside egui's window after the clamp; the death simply changed place). The new approach is upstream's own shape (`apps/photocraft/src/gpu_startup.rs`), adapted to where Android gets its window:
  1. **Preflight adapter ladder (android/src/gpu_ladder.rs), before `run_native`:** rungs `[vulkan, gl]` (desktop's ladder minus DX12/Metal, which do not exist on Android); with `WGPU_BACKEND` set, the single matching rung (`vulkan`; `gles`/`opengl`/`gl` → GL; `auto` → default ladder; any other value - e.g. `metal` - is recorded and left to eframe's default setup). Each rung: `Instance::new` mirroring egui-wgpu 0.36.2 `setup.rs::without_display_handle` (`InstanceFlags::from_build_config().with_env()`, `BackendOptions::from_env_or_default()`, `MemoryBudgetThresholds::default()`, `display: None`) pinned to the rung's backend; `block_on(instance.request_adapter(HighPerformance, no surface, apply_limit_buckets: false))` - the same field values egui's own request passes; then a device with **exactly `photocraft_ui_egui::gpu_canvas::device_limits(&adapter)`** (SU-9 restored verbatim); then a validation round trip: 64-byte `mapped_at_creation` write → `copy_buffer_to_buffer` → `submit` → `map_async` Read → `Device::poll(PollType::wait_indefinitely())` → `get_mapped_range` compare, all inside a **Validation error scope** (`Device::push_error_scope`), so a degenerate adapter's "Buffer size 64 is greater than the maximum buffer size (0)" (the api-31 SwiftShader Vulkan signature) becomes a clean recorded rejection instead of a panic. First validating rung → `egui_wgpu::WgpuSetup::Existing(WgpuSetupExisting { instance, adapter, device, queue })` (egui-wgpu 0.36.2 `setup.rs`: `new_instance()` returns `existing.instance.clone()` for Existing, and the window surface is created from `Painter.instance`, so surface/instance/adapter/device stay consistent; eframe injects the display handle only into CreateNew, which is skipped here). All rungs rejected → `WgpuSetup` untouched (upstream-identical failure).
  2. **Executor:** std-only `block_on` (~30 lines: `std::task::Wake` + `Mutex<bool>`/`Condvar`; native wgpu request futures complete on the first poll - wgpu 30.0.1 `Device::noop` poll-onces both with a noop waker - but the loop still waits properly on a real waker). `pollster` is deliberately NOT a direct dependency: `scripts/scope-guard.sh` line 11 (`ALLOW_EXT`) does not allow it, and R3 forbids changing a gate without the user's approval; eframe itself blocks on these same futures via its `pollster` feature dependency (already in Cargo.lock as a transitive dep).
  3. **Crash-safe marker (SU-8, minimal M1 form):** upstream's name/location (`gpu-starting.json` in the config dir); M1 content is the plain rung name (a future desktop-side Marker reader degrades it to an unknown-backend marker = same "died while starting" semantic; the desktop JSON shape needs serde parsing the shell does not carry). Advisory `File::try_lock` (Rust 1.89, toolchain ≥1.85) held for the whole ladder; busy lock → no skip, no writes (desktop "Busy" semantics); stale content → that rung is skipped with `rung {name}: skipped: a previous start died while starting on {name}`; written before each probe, cleared when a rung validates or the ladder ends. **M1 limitation recorded:** a hard crash AFTER a rung validated (surface creation, first frames) is not covered; desktop Sentinel parity is a later milestone.
  4. **Re-entry (directive 3):** after the run ends (clean or caught failure), android_main logs `Picsh: android_main done; exiting the process for a clean next launch` and `std::process::exit(0)`. Root cause of the relaunch class (R7, evidence run 39551410480): winit allows exactly one event loop per process, so a second `android_main` re-entry hit `EventLoopError` and left a dead-window process. Rotation never ends the loop (suspended/resumed are handled inside it), so only a finished run reaches the exit. Autosave: the M1 shell wires no autosave service (`services.autosave` is None; the pinned ui-egui per-frame autosave runs only where the service is set), so the directive's "flush autosave" is a logged no-op; preferences persist through eframe's `save_and_destroy` on loop end.
  5. **PHOTOCRAFT_TEST_CRASH knob:** debug-only `rungCrash` flavor asset (`applicationIdSuffix .crash`; `app/src/rungCrashDebug/assets/picsh-knobs.txt`), allowlisted in `jni_bridge.rs`. It fires at the END of the creator closure - AFTER the `device request:` and `SystemInfo:` evidence lines - so boot 1 reaches the ready marker before dying; one-shot via `picsh-test-crash.txt` in the config dir written BEFORE `std::panic::panic_any("PHOTOCRAFT_TEST_CRASH")` (no `panic!` literal; payload greppable; unwind caught in android_main → exit(0)); uninstalling the app clears the marker. The relaunch logs `PHOTOCRAFT_TEST_CRASH already fired once` and stays up.
  6. **CI (directive 3b):** `scripts/e2e-rung.sh` gains a scenario arg; two api-34 steps (`back`, `crash` on `rungCrashDebug`) gate re-entry: pid 1 must exit cleanly after Back (`Picsh: eframe loop returned cleanly`) / die with the `PHOTOCRAFT_TEST_CRASH` payload, then a relaunch with a new pid must reach the ready marker with exactly one fresh `device request:` line (and, for crash, the one-shot skip line). Both new gates are red-proven (seeded defect: the exit guard removal) per R3.

- **Amendment 5 (2026-10-21, Back re-entry red, runs 39615314265 + 39623279397 - NOT hypothesis):** the api-34 "Back press then relaunch" step went red with `pid 1 did not exit within 90s of Back` while the app itself was healthy (the failure-path capture of run 39623279397 shows the full PhotoCraft UI painted in `rungs/back/screenshot-red.png`, the ladder having selected `vulkan` on the SwiftShader adapter, the `device request:` line and the whole System Info block logged, and the pid-scoped logcat ending at the Back keypress: `D/gti.InputConnection(3753): onKey: KeyEvent {action=ACTION_DOWN, keyCode=KEYCODE_BACK ...}` + `D/picsh(3753): android_activity::activity_impl: Notifying Input Available`). Root cause, verified against the pinned sources: (1) the Back key DOES reach the app - winit 0.30.13 maps Android `Keycode::Back` to `Key::Named(NamedKey::BrowserBack)` (android/keycodes.rs `to_logical`: `Back => Key::Named(NamedKey::BrowserBack)`) and egui-winit 0.36.2 maps `NamedKey::BrowserBack` to `egui::Key::BrowserBack` (lib.rs:1516); egui 0.36.2 documents that variant as "Android sends this key on Back button press" (data/key.rs:190). (2) NOTHING acts on it: upstream `ui-egui` has no `BrowserBack` handling at all (only Escape), and neither did the shell. (3) The platform cannot rescue it either: the AGDK's GameActivity routes the key into the game's own input connection (so the framework never finishes the activity - `dumpsys` 90 s after the press still shows `topResumedActivity=...GameActivity`, `mCurrentFocus=...GameActivity`), and winit marks the key `Handled` (android/mod.rs `handle_input_event`: only the volume keys are reported `Unhandled`). So the run never ends and the pid stays alive. Fix (shell-only, no upstream change): the shell's app wrapper (`android/src/lib.rs`, `PlatformApp`) maps the Back key to the app-level "the user asked to leave" request, exactly as the desktop's window close does - `ctx.send_viewport_cmd(egui::ViewportCommand::Close)` on the root viewport - so upstream's own leave machinery decides what leaving means (unsaved-work prompt, saving-in-progress, and the platform quit in `Services::quit`; upstream `crates/ui-egui/src/discard_ui.rs:114-136`); the shell supplies that `Services::quit` hook (`android/src/services.rs`), which ends the process, because on Android a closed eframe window does NOT end the app: winit 0.30.13's Android backend never exits its event loop by itself (`MainEvent::Destroy` is an explicit "TODO: forward onDestroy notification to application" in winit's android/mod.rs). The CI gate for the Back scenario therefore greps the shell's leave line (`Picsh: leaving: the app quits`) instead of the impossible "eframe loop returned cleanly", and additionally asserts no Rust panic in the pid-1 logcat. The eframe close path itself is unchanged for the crash scenario (that knob still unwinds through `catch_unwind` in `android_main`).
